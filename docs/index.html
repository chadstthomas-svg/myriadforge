The device

A 12-core vector DSP, rescued from the drawer

The Myriad 2 (MA2450) is a USB accelerator Intel discontinued and dropped from OpenVINO after 2020.3. It can't run LLMs — but it's a genuinely capable, ~1 W always-on decision engine for static-shape FP16 workloads.

The measured ceiling

The ceiling is the model, not the chip

Paired-gap probes — each workload benched against a zero-compute twin with the identical input — isolate pure compute time on real silicon. The same chip that gives MobileNetV2 14.4 GFLOPS gives a dense 3×3 Conv stack 35.8 GFLOPS: the bottleneck is model structure, not the SHAVEs.

Where the speed comes from.

A newer host library can't make the firmware compute faster — single-inference latency is firmware-bound. The +48% comes from overlapping USB transfer with on-stick compute via multiple in-flight async requests. Model batching does not help on Myriad 2; pipelining does. Every number is measured on real silicon, with the limits documented.

And a capability shim.

Speed isn't the only gain. With --device hetero (HETERO:MYRIAD,CPU), ops the Myriad 2 can't compile — like the MobileNetV3-style HardSigmoid — fall back to the host CPU automatically. A graph pure MYRIAD rejects runs on the heterogeneous pipeline, widening the set of models the stick can accelerate.

Where the 58 ms actually goes.

Measured black-box (the plugin's own profiler crashes): 1.5 ms fixed dispatch, 14.8 ms input transfer (~40 MB/s), and 41.7 ms compute — running at just ~14 GFLOPS, about 10–18 % of the 80–150 GFLOPS peak. The device is compute-execution-bound, not USB-bound; the transfer share is precisely what pipelining hides (58.0 − 14.8 = 43.2 ms, the measured pipelined p50 to 0.01 ms). Bonus: FP16 input tensors are accepted and 4× faster (16.3 → 4.1 ms on the same graph) — the shim exposes that to every app.

The cascade, measured against Mirage.

The brain is expensive: Mirage costs 1.59 s per frame on the host CPU (720p) — 60 frames unguarded is 95 s. The stick screens all 60 in ~4.5 s at ~1 W. On our cartoon sample the gate fires on everything (an ImageNet top-1 gate is confidently wrong on abstract content) — the honest lesson: the gate needs task-specific semantics, and the harness now measures exactly that trade. On real footage where 1–5 % of frames fire, the same cascade cuts Mirage invocations 20–100×.

Trained for the job: four custom gates, physically evaluated.

The missing piece has been built — task-specific FP16 gates trained, deployed and scored on the real stick: voice commands (90.7 %, p95 3.89 ms), text intent routing (80.1 %, p95 3.08 ms), desktop control localization (89.2 %), and an experimental browser ranker — plus a rank-4 LoRA adapter for Cactus's own Needle 3. Datasets are CC BY 4.0 with full provenance. And MagicEightBall: a 131,072-token Boolean decision model whose smallest physically tested NCS1 build uses 480 bytes, with its Boolean policy retained on the stick.

Quickstart

Running in a few minutes

Native Windows only — the MYRIAD driver story is Windows-native, not WSL2.

# 1. Isolated OpenVINO 2020.3.2 venv for the NCS1 (idempotent)
powershell -ExecutionPolicy Bypass -File tools\ncs1\setup_env.ps1

# 2. WinUSB driver for the stick (one elevated run; approve UAC)
powershell -ExecutionPolicy Bypass -File tools\ncs2\install_driver.ps1

# 3. Functional smoke test (ONNX → FP16 IR → CPU vs onnxruntime)
tools\ncs1\.venv\Scripts\python.exe tools\ncs1\smoke_cpu.py

# 4. Discover lanes + a real benchmark on the stick
uv sync
uv run myriadforge devices
uv run myriadforge bench onnx-models/mobilenetv2-7 --device ncs1-myriad

# 5. Every pilot on the stick, one summary report
tools\ncs2\.venv\Scripts\python.exe tools\ncs2\demo_mvp.py --lane ncs1 --device myriad --full
